## 一、通用约定

路径规则、认证、响应格式、时间格式、字段命名、错误码 **沿用[文章模块接口文档](api_design.md)的第一章**，不重复。本模块与前两个模块的根本差异在这里：

| | 文章 / 计划模块 | AI 模块 |
|---|---|---|
| 依赖 | 纯本地，SQLite 就在硬盘上 | **依赖外部模型 API** —— 会断网、会限流、要花钱、单次要等几秒到几十秒 |
| 单个请求耗时 | 毫秒级 | 重建索引**分钟级**，问答**十秒级** |
| 跨模块 | 谁都不依赖谁 | **ai → article**，全项目唯一一处跨模块依赖 |
| 失败模式 | 只有业务失败 | 多了网络失败、限流、欠费、模型下线 |

因此本模块有三个前两个模块没有的形态：**后台任务**（F11）、**流式响应**（F12）、**阈值判定**（F13）。下面逐个说。

### 1.1 模型名必须可配置，不能写死

**这是本模块最容易在半年后炸掉的地方。**

阿里云百炼会定期下线旧模型（已公告 2026 年 10 月 10 日起分四批下线 100+ 个模型，含 `qwen-turbo`、`qwen3-max` 等）。模型下线后接口返回的是 **404 / model not found**，服务不会崩，但问答功能整个不可用。

所以模型名、维度、base_url **全部放进 `.env`**，代码里一个都不写死。换模型 = 改一行配置 + 点一次「重建索引」，不碰代码。

### 1.2 换 embedding 模型必须同时改维度和重建索引

`knowledge_chunk` 表里存了 `vector_dim` 和 `embedding_model` 两个字段（数据库设计时就留好了），就是为这件事。

旧模型生成的向量和新模型生成的向量**不在同一个向量空间**。混着用不会报错，只会检索出完全无关的内容 —— 是那种最难查的 bug。所以：

- 改 `AI_EMBEDDING_MODEL` 时**必须同时改** `AI_EMBEDDING_DIM`
- 改完**必须重建索引**（重建时全部块都会被新模型重新向量化）
- 状态接口会报告"有多少块是旧模型生成的"，用来提醒你还没重建

## 三、知识库构建（F11）

### 3.1 切块策略

文章正文用 `content_text`（纯文本），**绝不用 `content_html`** —— HTML 标签会污染语义匹配。这一条在文章保存环节就已经准备好了。

切块规则：

| 参数 | 默认 | 说明 |
|------|------|------|
| 目标块大小 | 500 字 | 中文按字符算 |
| 相邻重叠 | 100 字 | 防止答案正好被切在边界上、两边都不完整 |
| 边界优先级 | 段落 > 句子 > 硬切 | 依次尝试，实在没有边界才硬切 |

- **太短的尾块并进上一块**（低于 50 字），避免出现一堆没信息量的碎片
- 每块的文本 = **文章标题 + 换行 + 块内容**。标题是最强的检索信号（问「租房合同」时，标题里就有这四个字的文章应该排前面），代价是文章改标题后需要重建 —— 而重建本来就是手动的
- 分块序号 `chunk_index` 从 0 开始，同一篇文章内唯一（表上有 `uq_knowledge_chunk_article_index` 保证）

### 3.2 重建索引的流程

**全量重建，不是增量。** 理由：个人文章量级（几百篇）全量重跑一次的成本可以接受，而增量同步要维护"哪篇脏了"的状态，是复杂度的净增加。

1. 建/覆盖进度记录，状态置为 `running`
2. 调文章模块的 `list_article_ids()` 拿到**所有可检索的文章 ID**（已经在回收站里的不算）
3. 逐篇：`get_content()` 取正文 → 切块 → 批量向量化 → **先删该文章的旧块，再写新块**（同一事务，避免中途失败留下半新半旧）
4. 全部处理完后，删除 `article_id` 不在第 2 步白名单里的**孤儿块**（文章已被删除或进回收站留下的）
5. 进度置为 `done`，清空向量缓存

**单篇失败不中断整个任务**：记下失败篇数和最后一条错误信息，继续跑下一篇。理由是一个人写的文章里，偶尔有一篇内容异常不该让整个重建白跑。

**向量化必须分批**：百炼的 embedding 接口单次最多 **10 条**文本。分批大小写死 10，超过会被拒绝。

### 3.3 AI1 · 知识库状态

`GET /api/ai/kb/status`

**响应 200**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `article_count` | 整数 | 当前可检索的文章数 |
| `chunk_count` | 整数 | 知识库里的分块数 |
| `embedding_model` | 字符串 | 当前配置的向量化模型 |
| `embedding_dim` | 整数 | 当前配置的维度 |
| `stale_chunk_count` | 整数 | **有多少块不是当前模型生成的**（>0 说明该重建了） |
| `last_rebuilt_at` | 字符串 \| null | 上次成功重建的时间，带 `Z` |
| `last_error` | 字符串 \| null | 上次重建中最后一条错误信息（成功时为 null） |

`stale_chunk_count` 是给 1.2 节那个坑准备的：换了模型但忘了重建时，这个数字会大于 0。

### 3.4 AI2 · 触发重建

`POST /api/ai/kb/rebuild` → **202**

**立即返回，不等重建跑完**（全量重建是分钟级，HTTP 请求等不了）。

**响应 202**：`{ "status": "running", "total": 0, "done": 0 }`

**错误 409**：已经有一个重建任务在跑。不会排队，直接拒绝 —— 排队只会让用户等更久，而且连点两次基本是误操作。

**为什么不用 Celery / Redis**：那要额外装一个常驻服务，直接违背本项目「不装环境、省内存」的前提。这里用 FastAPI 的 `BackgroundTasks`，同一个进程里跑，零新增依赖。

> 代价要说清楚：任务是**进程内**的，服务重启就没了。所以启动时要做一次清理 —— 把状态还停在 `running` 的记录改成 `interrupted`，避免界面永远显示"正在重建"。

### 3.5 AI3 · 查重建进度

`GET /api/ai/kb/rebuild`

**响应 200**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | 字符串 | `idle` / `running` / `done` / `failed` / `interrupted` |
| `total` | 整数 | 本次要处理的文章数 |
| `done` | 整数 | 已处理篇数 |
| `failed` | 整数 | 其中失败的篇数 |
| `last_error` | 字符串 \| null | 最近一条错误信息 |
| `started_at` / `finished_at` | 字符串 \| null | 带 `Z` |

进度**存在数据库里而不是内存里**，这样关掉页面、换个设备再打开，进度还在。

前端在 `status === "running"` 时每 1.5 秒轮询这个接口，跑完就停。

## 四、智能问答（F12、F13）

### 4.1 一次提问发生了什么

```
问题文本
  → 向量化（1 次 embedding 调用）
  → 与知识库里所有分块算余弦相似度
  → 取分数最高的前 K 块（默认 5）
  → 最高分 >= 阈值？ ── 是 ─→ 把 K 块内容 + 问题交给模型，标注「引用了你的文章」(F12)
                     └─ 否 ─→ 只把问题交给模型，标注「未引用你的文章」(F13)
  → 流式输出回答
  → 存库（用户消息 + 助手消息 + 引用来源）
```

**F13 不是一个单独的接口**，它是同一个流程里的一个分支，靠阈值判定。这一点很重要：如果做成两个接口，前端就得先猜"我这个问题知识库里有没有"，猜错了再重发一次，浪费一次往返和一次 embedding 调用。

### 4.2 检索阈值是个需要调的参数

`AI_RETRIEVAL_MIN_SCORE` 默认 **0.35**，这是个初始猜测值，**第一次真实使用后要回来调**。

- 调太低 → 知识库里明明没有的问题，也会硬塞几段不相关的文章给模型，回答会变得牵强
- 调太高 → 明明有相关文章，却走了通用回答

调的方法：问答接口会把检索到的每块分数一起返回（见 4.3 的 `meta` 事件），观察几次真实问答的分数分布再定。

### 4.3 AI8 · 提问（SSE 流式）

`POST /api/ai/chat`

| 请求字段 | 类型 | 必填 | 约束 |
|----------|------|------|------|
| `session_id` | 整数 | 是 | 不传就先调 AI5 建一个 |
| `question` | 字符串 | 是 | 1~2000 字 |

**响应 `200`，`Content-Type: text/event-stream`** —— 不是普通 JSON。

**为什么要流式**：模型生成一段几百字的回答要 5~15 秒。不流式就是盯着转圈干等；流式是第一句出来就能开始读。

事件序列：

| 事件 | 时机 | 数据 |
|------|------|------|
| `meta` | **第一个**，检索一完成就发 | `{ "used_knowledge": true, "citations": [{"article_id":3,"title":"...","score":0.87,"chunk_index":2}] }` |
| `delta` | 反复，每次一小段 | `{ "text": "根据你的文章" }` |
| `done` | 最后 | `{ "message_id": 13 }` |
| `error` | 出错时 | `{ "detail": "模型接口调用失败：..." }` |

**`meta` 放在最前面是刻意的**：检索在生成之前就做完了，所以引用来源可以**立刻**显示出来，不用等回答生成完。用户能先看到"找到了这 3 篇"，再读回答。

**回答中途断掉怎么办**：服务端在生成过程中累积文本，放在 `try / finally` 里 —— 就算客户端关掉页面导致生成被取消，已经生成的部分也会存进数据库。宁可存半截，也不要留一个空回答。

### 4.4 提示词（Prompt）

两套 system prompt，靠阈值切换：

- **引用知识库**：把 K 块内容作为上下文给模型，要求"只依据以下内容回答，内容里没有的就说没有，不要编"
- **未引用知识库**（F13）：不给上下文，直接用通用能力回答

**把分块内容拼进 prompt 时要带上它来自哪篇文章**，否则模型没法在回答里说"根据《租房合同要注意什么》"。

## 五、会话管理（AI4~AI7）

| 接口 | 说明 |
|------|------|
| AI4 `GET /api/ai/sessions` | 会话列表，按更新时间倒序。**不分页** —— 单人自用，会话数量有限 |
| AI5 `POST /api/ai/sessions` | 新建会话，`{ "title": "..." }`，标题不传则默认「新对话」 |
| AI6 `GET /api/ai/sessions/{id}` | 会话详情，含全部消息（按时间正序） |
| AI7 `DELETE /api/ai/sessions/{id}` | 删除会话 → **204**，消息靠 ORM 级联一起删 |

**为什么不自动生成会话标题**：要额外调一次模型，占一次额度和一次延迟，收益很低。第一句提问的前 20 个字拿来做标题就够用了 —— 这个由前端在首次提问时做。

**删除为什么能连带删消息**：`ChatSession.messages` 上配了 `cascade="all, delete-orphan"`。**不能指望数据库的 `ON DELETE CASCADE`** —— 本项目没有开外键校验（见数据库设计），数据库不会做这件事，全靠 ORM 层。

## 六、前端调用约定

### 6.1 流式响应用 fetch，不用 EventSource

浏览器原生的 `EventSource` 有三个硬伤，正好全部命中本场景：

1. **只能 GET** —— 问题文本得塞进 query string。中文要编码，长度还有上限
2. **不能带自定义请求头**
3. **不能取消**（只能 `close()`，拿不到优雅的中止）

所以用 `fetch` + `response.body.getReader()` 手动解析 SSE 流。现代浏览器都支持，代码量也不大。

### 6.2 认证怎么带上

项目的登录态是 httpOnly Cookie，`fetch` 同源请求**默认就会带上**。但 Vite 开发时前端在 5173、后端在 8000，走的是代理，仍是同源 —— 不需要 `credentials: 'include'`。

### 6.3 模块文件划分

```
frontend/src/modules/ai/
├── api.ts          # AI1~AI7 的普通接口
├── chat.ts         # AI8 的流式请求（单独放，因为它和 axios 无关）
├── module.ts       # 模块登记（已有）
├── routes.ts       # 路由（已有）
└── views/
    ├── AiHomeView.vue    # 对话界面
    └── AiKbView.vue      # 知识库管理（状态 + 重建按钮 + 进度条）
```

## 七、实现要点与风险

| | 内容 | 应对 |
|---|---|---|
| 模型下线 | 百炼会定期下线旧模型，接口返回 404 | 模型名全部进 `.env`，代码不写死；报错信息里要带上当前用的模型名，方便排查 |
| 向量空间不一致 | 换了 embedding 模型但没重建，检索结果会莫名其妙且不报错 | `stale_chunk_count` 在状态接口里显式报出来 |
| 后台任务丢失 | `BackgroundTasks` 是进程内的，重启就没了 | 启动时把残留的 `running` 改成 `interrupted` |
| 流式中断 | 用户关页面导致回答没存 | 累积 + `try/finally`，存已生成的部分 |
| 批量上限 | 百炼 embedding 单次最多 10 条 | 分批大小写死 10 |
| 孤儿分块 | 文章删了但块还在，会被检索到 | 重建最后一步按白名单清理 |
| 跨模块 | ai 不能碰 article 的表 | 只调 `article/service.py` 的 `get_content()` / `list_article_ids()` |
| 检索缓存 | 每次检索都从磁盘读回全部向量，比检索本身还慢 | 进程内缓存，重建完成时置空，下次检索时懒加载 |
| 费用 | 每次问答要 1 次 embedding + 1 次对话调用 | 百炼新用户有免费额度；单次问答成本在分这个量级 |

### 8.2 实测记录（2026-09-30，本机）

**① 模型名核对**

`GET /models` 返回 261 个模型。`qwen3.7-flash` **在列表里**；`text-embedding-v4` **不在列表里，但接口调用正常**（返回 200、1024 维）—— 说明 `/models` 列的不全，判断模型是否可用**要以实际调用为准，不能只看列表**。

列表里另有 `qwen3.7-text-embedding` 和 `qwen3.7-text-embedding-flash` 两个新命名的向量模型。

**② 向量模型对比**（查询「租房的时候押金怎么才能要回来」，比较与一句相关句、一句无关句的余弦相似度）

| 模型 | 相关句 | 无关句 | 区分度 |
|------|--------|--------|--------|
| **text-embedding-v4** | 0.7242 | 0.2475 | **0.4768** |
| qwen3.7-text-embedding | 0.7240 | 0.2941 | 0.4299 |
| qwen3.7-text-embedding-flash | 0.7027 | 0.2750 | 0.4277 |

结论：**保持 `text-embedding-v4`**。单样本，差距不足以断言它更好，但它可用且区分度不差，没有换的理由。

**③ 思考模式（重要）**

同一个 RAG 问题（「根据资料：退租时房东无故扣押金，可先协商。问：押金能要回来吗？」）：

| | 耗时 | 思考 token | 回答 |
|---|---|---|---|
| 默认（开思考） | **9.6 秒** | **662** | 「押金**可以尝试要回**……」 |
| `enable_thinking=false` | **2.4 秒** | **0** | 「**能要回来。**根据资料描述……」 |

**结论：默认关闭思考模式。** 延迟和 completion token 都降到约 1/4。RAG 问答的任务是「从我的文章里找出来、归纳」，不是深度推理，4 倍代价换不到东西。

另一个必须记住的点：**开思考时，响应的 `message` / `delta` 里会多出一个 `reasoning_content` 字段**。代码里拼接回答必须**只取 `delta.content`** —— 一旦写成 `delta.get("content") or delta.get("reasoning_content")` 之类，模型的内心独白会直接漏进用户看到的回答里。关掉思考模式后这个字段不会出现，但代码不能依赖这一点。

**④ 流式**

`stream=True` + `stream_options={"include_usage": true}` 正常：首字延迟 0.00 秒，`delta` 里只出现 `content` 和 `role` 两个字段，`[DONE]` 正常结束，末尾的 usage 块能收到。
