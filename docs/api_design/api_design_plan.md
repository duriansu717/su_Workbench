## 一、通用约定

路径规则、认证、响应格式、时间格式、字段命名、错误码 **完全沿用[文章模块接口文档](api_design.md)的第一章**，这里不重复。只有三处不同：

| | 文章模块 | 计划模块 | 为什么不同 |
|---|---|---|---|
| 更新方式 | `PUT`（全量） | **`PATCH`（部分）** | 文章编辑是一个完整表单，提交时所有字段都在手边；待办的"勾选完成"只改一个字段，用全量更新就得先把整条待办读出来再原样提交回去，多一次往返，而且中间任何字段读漏了都会被静默覆盖 |
| 分页 | 有 | **没有** | 待办的查询范围由日期区间限定（日 / 周 / 月），天然有界；收集箱也不会无限增长。真需要了再加 |
| 删除 | 软删除 + 回收站 | **物理删除** | 回收站是 F5 对文章的要求，待办没有这条。做完就打勾了，留回收站只会让收集箱越来越乱 |

### 1.1 `planned_date` 是日历日期，不是时间戳

接口里它的形状是 `"2026-10-01"` —— **不带时间、不带 `Z` 后缀、不做任何时区转换**。

这条对计划模块比对任何模块都重要：日 / 周 / 月三种视图**全都是在拿这个字段做范围查询**。一旦它被当成时间戳按时区转换，中国是 UTC+8，每一条待办都会往前挪一天，而且**不报任何错**——你会看到"计划 10 月 1 日做的事"显示在 9 月 30 日。

## 二、接口总览

| 编号 | 方法 | 路径 | 说明 | 对应功能 |
|------|------|------|------|----------|
| P1 | GET | `/api/plan/todos` | 待办列表（日期区间 / 完成状态 / 收集箱筛选） | F9、F10 |
| P2 | POST | `/api/plan/todos` | 新建待办 | F9 |
| P3 | PATCH | `/api/plan/todos/{id}` | 部分更新（含勾选完成） | F9 |
| P4 | DELETE | `/api/plan/todos/{id}` | 删除待办 | F9 |

**F10 的三种视图共用 P1 一个接口**，区别只是前端传的日期区间不同：

| 视图 | from / to |
|------|-----------|
| 日 | 当天 / 当天 |
| 周 | 本周一 / 本周日 |
| 月 | 当月 1 日 / 当月最后一天 |

**周从周几开始由前端算，不由后端算。** 这是展示层的约定（中国习惯周一起，有些地方周日起），后端不该替前端决定。后端只认 `from` 和 `to`。

## 三、P1 · 待办列表

`GET /api/plan/todos`

| 查询参数 | 类型 | 默认 | 说明 |
|----------|------|------|------|
| `from` | 日期 | 无 | 计划日期 **>=** 该日（含） |
| `to` | 日期 | 无 | 计划日期 **<=** 该日（含） |
| `is_done` | 布尔 | 无 | 不传返回全部；传 `true` / `false` 只看已完成 / 未完成 |
| `unscheduled` | 布尔 | `false` | 传 `true` 时**只返回没有计划日期的**（收集箱），此时忽略 from / to |

**响应 200**：一个数组（不分页）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | 整数 | |
| `title` | 字符串 | |
| `note` | 字符串 \| null | 备注 |
| `planned_date` | 字符串 \| null | `"2026-10-01"`，**不带时间**。null 表示还没安排 |
| `priority` | 整数 | 1 高 / 2 中 / 3 低 |
| `is_done` | 布尔 | |
| `done_at` | 字符串 \| null | 完成时间，带 `Z` |
| `created_at` / `updated_at` | 字符串 | 带 `Z` |

**排序**：计划日期升序（**没日期的排最后**）→ 优先级升序（1 高在前）→ id 升序。

> 实现要点：这个"没日期的排最后"靠 SQLite 的一个特性实现 ——
> `ORDER BY planned_date IS NULL, planned_date, ...`。
> `planned_date IS NULL` 在 SQLite 里求值为 0 或 1，升序排列时 0（有日期）自然排在 1（没日期）前面。
> 如果直接写 `ORDER BY planned_date`，NULL 会排在最前面（SQLite 里 NULL 最小），收集箱里的待办会挤在每一天视图的最上面。

## 四、P2 · 新建待办

`POST /api/plan/todos`

| 请求字段 | 类型 | 必填 | 约束 |
|----------|------|------|------|
| `title` | 字符串 | 是 | 1~200 字 |
| `note` | 字符串 | 否 | |
| `planned_date` | 日期 | 否 | 不传 = 还没安排，进收集箱 |
| `priority` | 整数 | 否 | 默认 2（中）；**只允许 1 / 2 / 3** |

**响应 201**：新建出来的待办（字段同 P1 的一项）
**错误 422**：`priority` 不在 1 / 2 / 3 里。这是字段范围约束，由 Pydantic 自动返回，
不需要自己抛异常 —— 和文章模块错误码表里 400（业务规则不满足）
与 422（请求根本不符合接口定义）的区分是一致的

## 五、P3 · 部分更新

`PATCH /api/plan/todos/{id}` —— **所有字段可选**，只改传上来的

| 字段 | 说明 |
|------|------|
| `title` / `note` / `planned_date` / `priority` | 同 P2 |
| `is_done` | 勾选完成 / 取消完成 |

**`is_done` 有副作用，而且由服务端负责**：

- 改成 `true` → 自动写入 `done_at` 为当前时间
- 改回 `false` → 自动清空 `done_at`

**`done_at` 不接受客户端传值**，否则可以伪造完成时间。它甚至不出现在请求体里。

**响应 200**：更新后的待办
**错误 404**：待办不存在
**错误 422**：`priority` 不在 1 / 2 / 3 里（同 P2）

## 六、P4 · 删除

`DELETE /api/plan/todos/{id}` → **204**

物理删除，没有回收站（理由见第一章的表格）。计划模块不引用任何其他模块的表，删起来没有连带影响。

**错误 404**：待办不存在

## 七、前端调用约定

调用统一放在 `frontend/src/modules/plan/api.ts`，用 `core/api.ts` 的 axios 实例。

```
planApi.todos.list / create / update / remove
```

**日期参数要用本地日期拼，不能用 `toISOString()`。** 这是最容易踩的一处：

```ts
// ✗ 错：toISOString 会先转成 UTC，中国时区下 10 月 1 日会变成 "2026-09-30"
new Date(2026, 9, 1).toISOString().slice(0, 10)   // "2026-09-30"

// ✓ 对：直接拼本地年月日
const ymd = (d: Date) =>
  `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}-${String(d.getDate()).padStart(2, '0')}`
```

`planned_date` 是日历日期，**从生成的那一刻起就不该经过时区转换** —— 一旦用了 `toISOString`，你就又把 UTC 引进来了，而这正是这整个模块最需要避免的事。

## 八、实现要点与风险

| | 内容 | 应对 |
|---|---|---|
| 日期序列化 | `planned_date` 必须返回 `"2026-10-01"`，**不能带 `Z` 也不能带时间** | 用 Pydantic 的 `date` 类型（默认就是这个形状），不要手滑改成 `datetime` |
| `done_at` | 只由服务端在 `is_done` 变化时维护 | 请求模型里根本不放这个字段 |
| 排序 | 没日期的要排最后 | `ORDER BY planned_date IS NULL, planned_date, priority, id`，见 P1 的说明 |
| 前端日期 | 用本地年月日拼字符串，不要用 `toISOString()` | 见第七章 |
| 周起始 | 周一还是周日由前端定 | 后端只认 from / to，不猜 |
| 时区 | 时间戳沿用带 `Z` 的约定 | 同文章模块 |

## 九、下一步

接口实现完成后，**用架构设计文档第八章的清单跑一遍验收**。

这个模块的特殊之处在于：文章、计划、AI 三个模块的骨架是一开始就搭好的，这是第一个真正"从零走一遍"的模块。验收方法是：

```bash
git diff --stat
```

改动范围应该只有 **计划模块自己的文件 + 两个注册表各一行**。如果 diff 里出现了 `article/` 或 `ai/` 目录下的文件，说明模块边界破了 —— 而那比修一个 bug 重要得多，因为它意味着每加一个模块都会更贵。
