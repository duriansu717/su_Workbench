# Freedom Design 个人工作台 接口设计文档（文章模块）

> 文档版本：v1.0
> 生成日期：2026-09-29
> 上游依赖：docs/feature_list/feature_list.md（F2~F8）、docs/database/database.md、docs/architecture/architecture.md

本文档只覆盖**文章模块**（功能清单 F2~F8）。第一章的通用约定是全局的，计划模块和 AI 模块的接口在各自开发时按同一套约定补。

## 一、通用约定

### 1.1 路径规则

```
/api/{模块名}/{资源}
```

| 模块 | 前缀 | 本文档涉及的资源 |
|------|------|------------------|
| 文章 | `/api/article` | `articles`、`categories`、`tags`、`uploads` |

骨架层自己的接口（健康检查、认证）不走这套规则，它们直接挂在 `/api` 下——因为认证不是模块，见架构设计 3.1 节。

> **一个看起来有点啰嗦的地方**：文章资源是 `/api/article/articles`，`article` 出现了两次。这是模块前缀和资源名撞车导致的。我**故意没去消除它**——另一个选择是把文章资源提到模块根（`/api/article`），但那样 `/api/article/{id}` 和 `/api/article/categories` 就会长得一样，只能靠路由注册顺序区分，非常脆弱。**啰嗦但无歧义，胜过简洁但要看顺序。**

### 1.2 认证

- 除登录接口外，**所有接口都要求登录**：依赖 `core/deps.py` 的 `get_current_user`，它从 httpOnly Cookie 里读 JWT
- 未登录或 token 过期一律返回 **401**，前端拦截器负责跳登录页
- 单人系统，没有角色和权限分级：登录了就是全部权限

### 1.3 请求与响应格式

- 请求体和响应体一律 **JSON**（图片上传除外，用 `multipart/form-data`）
- 响应**不套一层 `{code, data, message}` 信封**。直接用 HTTP 状态码表达结果，成功时响应体就是数据本身

  理由：信封是给"所有接口都返回 200、靠 body 里的 code 区分"那种设计的。我们既然用了 HTTP，就让状态码干活——前端用 axios 拦截器统一处理 `401`、`404` 这些，只需要一处逻辑。套了信封反而每个调用点都要多剥一层。

- 创建成功返回 **201**，删除成功返回 **204**（无响应体），其余成功返回 **200**

### 1.4 分页

列表接口统一用这两个参数：

| 参数 | 类型 | 默认 | 约束 |
|------|------|------|------|
| `page` | 整数 | 1 | 最小 1 |
| `page_size` | 整数 | 20 | 最小 1，最大 100 |

响应统一长这样：

```json
{ "items": [], "total": 137, "page": 1, "page_size": 20 }
```

`total` 是**过滤后的总数**，不是全表总数——前端要靠它算总页数。

### 1.5 时间格式

**所有时间字段返回带 `Z` 后缀的 ISO 8601 字符串**，例如 `"2026-09-29T15:30:00Z"`。

这一条很重要，写错了会静默出错：数据库里存的是**不带时区信息的 UTC 时间**（见数据库设计第一章），如果接口返回 `"2026-09-29T15:30:00"` 这种没有时区标记的字符串，前端 `new Date()` 会**把它当成当地时间**解析——中国是 UTC+8，显示出来会差 8 小时，而且不报任何错。

带 `Z` 之后 `new Date("2026-09-29T15:30:00Z")` 才会正确识别为 UTC 并转成本地时间。

**例外**：`todo.planned_date` 是日历日期，返回 `"2026-10-01"`，不带时间也不带 `Z`——它本来就不涉及时区。

### 1.6 字段命名

- 接口字段一律 **snake_case**（`category_id`、`page_size`），和数据库、Python 保持一致
- 前端 TypeScript 侧同样用 snake_case，**不做驼峰转换**。多一层转换就是多一个出错的地方，而且前后端字段名不一致时排查很费劲

### 1.7 错误处理

错误响应统一是 FastAPI 的默认形状：

```json
{ "detail": "分类「生活」下还有 12 篇文章，不能删除" }
```

`detail` 是可以**直接显示给用户的中文**。前端不需要自己映射错误码到文案。

## 三、分类接口（F6）

### 3.1 A1 · 分类列表

`GET /api/article/categories` —— 无参数，不分页（分类是有限集合）

**响应 200**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | 整数 | |
| `name` | 字符串 | |
| `sort_order` | 整数 | 越小越靠前 |
| `article_count` | 整数 | **未删除**的文章数，用于列表页展示和删除前提示 |

### 3.2 A2 · 新建分类

`POST /api/article/categories`

| 请求字段 | 类型 | 必填 | 约束 |
|----------|------|------|------|
| `name` | 字符串 | 是 | 1~50 字，不能与已有分类重名 |
| `sort_order` | 整数 | 否 | 默认 0 |

**响应 201**：同 A1 的单项。
**错误 409**：`分类「生活」已存在`

### 3.3 A3 · 改名 / 排序

`PUT /api/article/categories/{id}` —— 两个字段都可选，只传要改的

**响应 200**：同 A1 的单项。
**错误 404**：分类不存在；**409**：改成的新名字已存在

### 3.4 A4 · 删除分类

`DELETE /api/article/categories/{id}`

**这是本项目里最需要小心的一类接口。** 数据库没有启用外键校验（见数据库设计第七章），删掉一个还有文章在用的分类，数据库**不会拦住你**——那些文章会变成分类显示不出来的孤儿，而且不报错。

所以这个接口必须在删除前主动检查：

**响应 204**：成功
**错误 409**：`分类「生活」下还有 12 篇文章，不能删除`

> 这条检查由 `service.py` 负责，**不能写在 router 里**——router 只做参数校验和调用 service。判断标准是：任何删除操作，都要先问一句「有没有别的表在引用它」。

## 四、标签接口（F7）

### 4.1 A5 · 标签列表

`GET /api/article/tags` —— 字段为 `id`、`name`、`article_count`（未删除文章数）

### 4.2 A6 · 新建标签

`POST /api/article/tags`，请求体 `{ "name": "租房" }`
**响应 201** / **错误 409** 重名

### 4.3 A7 · 改名

`PUT /api/article/tags/{id}`，请求体 `{ "name": "..." }`

### 4.4 A8 · 删除标签

`DELETE /api/article/tags/{id}`

和分类不同，**这里不需要检查引用**：删标签只是把它从所有文章上摘掉，中间表 `article_tag` 里的关联行由 SQLAlchemy 的 `secondary` 关系自动清理（数据库设计 7.3 节）。

**响应 204**
**错误 404**：标签不存在

## 五、文章接口（F2、F4、F5、F8）

### 5.1 A9 · 文章列表

`GET /api/article/articles`

| 查询参数 | 类型 | 默认 | 说明 |
|----------|------|------|------|
| `page` | 整数 | 1 | |
| `page_size` | 整数 | 20 | 最大 100 |
| `keyword` | 字符串 | 无 | 同时匹配标题和正文纯文本（F8） |
| `category_id` | 整数 | 无 | 按分类筛选 |
| `tag_id` | 整数 | 无 | 按标签筛选 |
| `status` | 字符串 | `published` | `published` 或 `deleted`（回收站） |

排序固定为 **`updated_at` 倒序**，不接受参数——功能清单 F8 明确要求按时间排序。

**响应 200** 的 `items` 每一项：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | 整数 | |
| `title` | 字符串 | |
| `excerpt` | 字符串 | 从 `content_text` 截取前 120 字。**列表页不返回完整正文**，几十篇文章的 HTML 全带上会让响应体大得没必要 |
| `category` | 对象 | `{id, name}` |
| `tags` | 数组 | `[{id, name}]` |
| `status` | 字符串 | |
| `created_at` / `updated_at` | 字符串 | 带 `Z` 的 ISO 8601 |

> **实现要点**：列表要带上 category 和 tags，如果每篇文章各查一次就是 N+1 查询。必须用 `selectinload` 预加载，否则 20 篇文章会打出 40 多次查询。

### 5.2 A10 · 文章详情

`GET /api/article/articles/{id}` —— 在上面字段基础上多返回 `content_html`（编辑器回填用）和 `deleted_at`。

**不返回 `content_text`**：那是给搜索和 AI 用的内部字段，前端不需要。

**错误 404**：文章不存在

### 5.3 A11 · 新建文章

`POST /api/article/articles`

| 请求字段 | 类型 | 必填 | 约束 |
|----------|------|------|------|
| `title` | 字符串 | 是 | 1~200 字 |
| `content_html` | 字符串 | 是 | 富文本正文 |
| `category_id` | 整数 | 是 | 必须存在 |
| `tag_ids` | 整数数组 | 否 | 默认空数组；不存在的 ID 直接忽略 |

**请求里没有 `content_text`**，这是有意的：纯文本由服务端从 `content_html` 抽取。

理由：数据库设计第一章要求"这两个字段必须在同一个 service 函数里一起写"。如果让客户端传，就有了"只更新一个"的可能，而两者一旦不同步，搜索和 AI 检索会读到旧内容，**且没有任何报错**。服务端抽取是唯一能保证同步的做法。

**服务端处理顺序**（顺序不能换）：

1. 用 `nh3` 对 `content_html` 做白名单消毒，**过滤掉 `<script>`、事件属性、`javascript:` 链接等**
2. 从**消毒后**的 HTML 抽取纯文本（用 `beautifulsoup4`）
3. 两个字段一起写入

先消毒再抽取，顺序反了会把本该被过滤掉的脚本内容抽进纯文本里。

**响应 201**：同 A10 的详情
**错误 400**：`分类不存在`；**422**：字段格式不合法（Pydantic 自动）

### 5.4 A12 · 更新文章

`PUT /api/article/articles/{id}` —— 请求体字段同 A11，**全量更新**（编辑器表单里本来就带着全部字段）

服务端处理同 A11，同样会重新消毒并重新抽取纯文本。

**响应 200**：详情 / **404** / **400**

### 5.5 A13 · 移入回收站

`DELETE /api/article/articles/{id}`

软删除：把 `status` 置为 `deleted`、写入 `deleted_at`，**数据行保留**（F5 要求能还原）。

**响应 204** / **404**

### 5.6 A14 · 从回收站还原

`POST /api/article/articles/{id}/restore`

把 `status` 置回 `published`、清空 `deleted_at`。

**响应 200**：详情 / **404** / **409**：`文章不在回收站里`

### 5.7 A15 · 彻底删除

`DELETE /api/article/articles/{id}/force`

**不可恢复。** 物理删除数据行，同时清掉它的标签关联（由 ORM 的 `secondary` 关系自动完成）。

本模块**不负责**清理 AI 模块的知识库分块——原因见第九章第 2 条。

**响应 204** / **404**

## 六、图片上传（F3）

### 6.1 A16 · 上传正文插图

`POST /api/article/uploads/images` —— `multipart/form-data`，字段名 `file`

| 校验项 | 规则 |
|--------|------|
| 允许的类型 | `image/png`、`image/jpeg`、`image/gif`、`image/webp` |
| 单个文件大小 | 不超过 5 MB |
| 文件名 | **不信任客户端传来的文件名**，用 UUID 重新生成 |

**存储位置**：`backend/uploads/images/{YYYY-MM}/{uuid}.{ext}`

**为什么重新生成文件名**：客户端传来的文件名可能包含 `../` 或非法字符，直接使用会造成路径穿越——上传一个叫 `../../app/main.py` 的"图片"，就能覆盖源码。用 UUID 生成文件名是标准做法。

**响应 201**

```json
{ "url": "/uploads/images/2026-09/3f2a1b4c.png", "size": 204800 }
```

**错误 400**：类型不支持；**413**：文件超过 5 MB

**静态访问**：`/uploads` 由 `main.py` 挂载 `settings.upload_path` 提供（`core` 的事，不是本模块的事）。这些文件在 `.gitignore` 里，不进版本库。

**注意**：上传接口**只存文件，不碰数据库**。图片什么时候真正和文章关联，取决于编辑器把返回的 URL 插进了正文 HTML —— 那一步在保存文章时（A11/A12）自然完成。所以上传了但没保存的文章，图片会变成没人引用的孤儿文件，这是可接受的。

## 七、错误码表

| 状态码 | 含义 | 什么时候返回 | 前端怎么处理 |
|--------|------|--------------|--------------|
| 200 | 成功 | 查询、更新 | 正常使用响应体 |
| 201 | 创建成功 | 新建文章 / 分类 / 标签 / 上传图片 | 同上 |
| 204 | 成功无内容 | 所有删除操作 | 不读响应体 |
| 400 | 业务规则不满足 | 如 `分类不存在`、图片类型不支持 | 直接显示 `detail` |
| 401 | 未登录 / 登录过期 | 任何需要登录的接口 | **拦截器统一跳登录页**，业务代码不用管 |
| 404 | 资源不存在 | 按 ID 找不到文章 / 分类 / 标签 | 提示并返回列表页 |
| 409 | 状态冲突 | 分类重名、删除仍有文章的分类、还原不在回收站的文章 | 直接显示 `detail` |
| 413 | 请求体过大 | 图片超过 5 MB | 提示换小图 |
| 422 | 参数格式不合法 | 缺必填字段、类型不对（**FastAPI 自动返回**） | 一般不出现。**出现了说明前端有 bug**，因为正常的表单校验应该在前端就拦住 |

**注意 400 和 422 的区别**：422 是"你这请求根本不符合接口定义"，400 是"请求形式没问题，但业务上不成立"。前端只需要处理 400、404、409 的 `detail`，401 交给拦截器。

## 八、前端调用约定

文章模块的接口调用统一放在 `frontend/src/modules/article/api.ts`，用 `core/api.ts` 的 axios 实例（它已经配好了 baseURL、Cookie 和 401 拦截）。

按资源分组：

```
articleApi.categories.list / create / update / remove
articleApi.tags.list / create / update / remove
articleApi.articles.list / get / create / update / remove / restore / forceRemove
articleApi.uploads.image(file)
```

**不要在组件里直接写 `axios.get('/article/articles')`** —— 所有路径集中在 `api.ts`，改路径时只动一处。

## 九、实现要点与风险

| 类型 | 内容 | 应对 |
|------|------|------|
| 依赖 | 富文本消毒与纯文本抽取需要两个新包：`nh3` 0.3.7（Rust 的 ammonia 绑定，做白名单消毒）、`beautifulsoup4` 4.15.0（抽纯文本）。**bleach 已停止维护，不要用** | 实现时加进 `requirements.txt`，并同步技术栈文档的依赖清单 |
| 顺序 | **必须先消毒再抽纯文本** | 反了会把本该过滤的内容抽进纯文本，而纯文本是喂给 AI 的 |
| 风险 | **删除分类不检查引用会静默产生孤儿文章** | A4 的检查必须实现在 service 层，见 3.4 |
| 风险 | 列表接口 N+1 查询 | 必须用 `selectinload` 预加载 category 和 tags |
| 风险 | 时间戳少了 `Z` 后缀，前端显示会差 8 小时且不报错 | 序列化时统一补 `Z`，见 1.5 |
| 风险 | 上传文件名被用于路径穿越 | 一律用 UUID 重命名，见 6.1 |
| 风险 | **删除文章不会清理 AI 知识库** | 见下方第 2 条 |

### 关于「彻底删除文章后，AI 知识库里的分块怎么办」

`knowledge_chunk.article_id` 是**软引用，没有外键**（数据库设计 6.3 节）。彻底删除一篇文章，它的分块不会自动消失。

而且这里有个**依赖方向的问题**：文章模块不能反过来调用 AI 模块去清理，因为架构设计定的是单向依赖 `ai → article`。文章模块反向依赖 AI，就成环了。

**解决办法在 AI 模块一侧，不在文章模块**：

1. **检索时过滤**：AI 模块查分块时，先排除掉那些文章已经不存在的分块。这保证**答案里永远不会出现已删除文章的内容**——这是正确性问题，必须解决
2. **重建索引时清理**：F11 的「重建索引」本来就要遍历所有文章，顺手删掉孤儿分块即可。这只是省空间，不及时做也不影响正确性

所以本模块只管把文章删干净，**不管知识库**。AI 模块开发时按上面两条实现。
