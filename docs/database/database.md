## 一、设计原则

这些决定贯穿全部表，后面不再重复解释。

| 原则 | 做法 | 理由 |
|------|------|------|
| 主键 | 全部用自增整数 `INTEGER PRIMARY KEY` | 单人自用，不存在多端离线合并的场景，UUID 换来的分布式友好性用不上，却要多占一倍空间、索引也更慢 |
| 时间 | 统一存 UTC 的 `DATETIME`，前端负责转本地时区 | SQLite 不存时区信息，不统一约定的话，某天你换个时区或出个差，所有时间就全乱了 |
| **日历日期** | `todo.planned_date` 存 `DATE`，**不做时区转换** | 这条和上一条不矛盾，要分清：「文章创建于几点几分」是一个瞬间，要按时区转换；「这件事计划在 10 月 1 日做」是一个日历上的格子，换算成 UTC 会平白偏移一天 |
| 软删除 | 文章用 `status` 字段标记，不做物理删除 | 功能清单 F5 要求删除后能进回收站并还原 |
| 模块归属 | 每张表只属于一个模块，表名前缀不加模块名 | 架构设计第五章铁律一：模块只碰自己的表。不加前缀是因为 SQLAlchemy 的模型类已经按目录分好了，SQLite 里也没有 schema 概念 |
| 外键 | 模型里声明外键，但**不启用数据库校验**（不设置 `PRAGMA foreign_keys`） | 见第六章第 7 条。这是本项目的明确取舍，代价必须清楚 |
| 不加 user_id | **所有业务表都不设 user_id 外键** | 见第六章第 5 条 |
| 枚举值 | 用字符串或整数存，**不加数据库 CHECK 约束**，合法性在应用层用 Python 枚举 + Pydantic 校验 | SQLite 修改 CHECK 约束要整表重建，成本高；而值的合法性本来就更适合在应用层表达 |
| 字符串长度 | 标题 200、名称 50、摘要 500，正文和备注用无限长的 `TEXT` | SQLite 实际不强制长度，声明长度是为了将来万一换 PostgreSQL 时不用改 |

### 3.6 todo（计划模块）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | 主键 | |
| `title` | VARCHAR(200) | 非空 | 待办内容 |
| `note` | TEXT | 可空 | 备注 |
| `planned_date` | DATE | 可空 | 计划日期。**日历日期，不做时区转换**；为空表示还没安排到具体某天 |
| `priority` | INTEGER | 非空、默认 2 | 1 高 / 2 中 / 3 低。用整数是为了能直接排序，不用写 CASE |
| `is_done` | BOOLEAN | 非空、默认 否 | 是否完成 |
| `done_at` | DATETIME | 可空 | 完成时间 |
| `created_at` | DATETIME | 非空 | |
| `updated_at` | DATETIME | 非空 | |

F10 的日 / 周 / 月三种视图**用的是同一份数据**，区别只是查询时对 `planned_date` 取不同的范围——日视图查当天，周视图查本周一到周日，月视图查当月。所以这里是三张视图一张表，而不是三张表。

`planned_date` 为空的待办不会出现在任何视图里，相当于一个「收集箱」，先记下来回头再安排。

### 3.7 knowledge_chunk（AI 问答模块）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | 主键 | |
| `article_id` | INTEGER | 非空，**无外键约束** | 软引用，见第六章第 3 条 |
| `chunk_index` | INTEGER | 非空 | 这是该文章的第几块，从 0 开始 |
| `chunk_text` | TEXT | 非空 | 切块后的纯文本，**来自 `article.content_text`，绝不来自 `content_html`** |
| `vector` | BLOB | 非空 | 向量，float32 原始字节。见第六章第 2 条 |
| `vector_dim` | INTEGER | 非空 | 向量维度，如 1024 |
| `embedding_model` | VARCHAR(100) | 非空 | 生成该向量的模型标识 |
| `updated_at` | DATETIME | 非空 | |

唯一约束 `(article_id, chunk_index)`。

`vector_dim` 和 `embedding_model` 这两个字段是刻意加的：**以后你换 embedding 模型时，需要知道哪些块是旧模型生成的**。换模型后旧的向量和新问题不在同一个向量空间里，混用会检索出完全无关的内容，而且这种错误不会报错，只会让回答变得莫名其妙。有了这两个字段，重建时可以精确地只处理不匹配的块。

## 四、关系说明

```
                         user（全局，只有一条记录）
                          （业务表不引用它，见第六章第 5 条）

  ┌─────────────── 文章模块 ───────────────┐
  │                                        │
  │  category ──1:N──▶ article ──1:N──▶ article_tag ◀──N:1── tag
  │                      │                  （多对多中间表）
  │                      │
  └──────────────────────┼─────────────────┘
                         │ 软引用（无外键）
                         ▼
  ┌─────────────── AI 问答模块 ─────────────┐
  │                                        │
  │  knowledge_chunk                       │
  │                                        │
  │  chat_session ──1:N──▶ chat_message    │
  │                                        │
  └────────────────────────────────────────┘

  ┌─────────────── 计划模块 ────────────────┐
  │  todo（独立，不引用任何表）              │
  └────────────────────────────────────────┘
```

三条需要说明的地方：

1. **`article` → `article_tag` → `tag` 是标准的多对多**。一篇文章可以有多个标签，一个标签可以属于多篇文章。
2. **AI 模块到文章模块是单向软引用**。`knowledge_chunk.article_id` 指向文章，但没有数据库层面的外键约束。方向是单向的 `ai → article`，文章模块完全不知道 AI 模块存在。原因见架构设计第七章。
3. **计划模块完全独立**，不和其他模块产生任何关系。这正好是架构设计里说的"模块化竖切"最纯粹的一个例子。

## 五、索引设计

SQLite 会为主键和唯一约束自动建索引，下面只列需要额外建的。

| 表 | 索引字段 | 理由 |
|----|----------|------|
| `article` | `category_id` | F8 按分类筛选，以及列表页按分类展示 |
| `article` | `(status, updated_at)` | 列表页和搜索几乎总是「过滤掉已删除」+「按更新时间倒序」一起出现。**不另建 `status` 单列索引**——联合索引的左前缀已经能单独服务它；**也不建 `updated_at` 单列索引**——查询总会带上 status，用不上 |
| `article_tag` | `tag_id` | 联合主键已经覆盖了 `article_id` 开头的查询，反过来按标签查文章需要单独建 |
| `todo` | `(is_done, planned_date)` | 日 / 周 / 月视图的查询条件就是「未完成 + 日期在某范围内」 |
| `knowledge_chunk` | `article_id` | 重建某篇文章的索引时要按它批量删除 |
| `chat_message` | `session_id` | 打开会话时按它取全部消息 |

**关于 `article.title` 和 `article.content_text` 不建索引**：F8 的关键词搜索用的是 `LIKE '%关键词%'`，前缀带通配符的查询用不上索引。原因见第六章第 6 条。

## 六、关键设计决策说明

前五章是"是什么"，这一章是"为什么这么定"。如果你以后想改，先看这里。

### 1. 文章为什么存两份正文

`content_html` 给编辑器和页面渲染用，`content_text` 给搜索和 AI 切块用。

富文本底层是 HTML，里面有 `<p>`、`<span style="...">` 这些标签。**这些标签直接喂给 AI 检索会严重拉低效果**——模型会把标签当成正文内容的一部分，切出来的块既浪费额度又干扰语义匹配。

而"保存时顺手抽一份纯文本"现在几乎零成本；等你攒了几百篇再回头补，就得把每篇重新解析一遍。这是功能清单第六节就定下的约束，数据库这一层落实成两个字段。

### 2. 向量为什么存 BLOB 而不是拆成多列

向量直接以 float32 的原始字节存进 `BLOB` 字段，维度记在 `vector_dim` 里。

拆成 `v1, v2, ... v1024` 这种多列是灾难——每换一次 embedding 模型维度就变了，表结构也得跟着改。存成字节流则对维度完全透明。

性能上没问题：技术栈文档 3.7 节有实测数据，16000 个 1024 维向量存进 SQLite 再读回来完全无损，占用约 70 MB。**但要注意：服务启动时应该把向量一次性读进内存缓存**，因为从磁盘读回（实测 192ms）比检索本身（3.68ms）还慢五十倍。

### 3. knowledge_chunk.article_id 为什么不建外键

因为架构设计第五章的铁律一：模块之间不碰对方的表。

如果建了外键，两张表就在数据库层面绑死了——AI 模块的文章引用会被文章模块的表结构变化牵动，将来想把 AI 模块拆出去独立部署时，这个外键会变成障碍。

代价是引用完整性要靠代码保证（比如删文章时要顺带清理它的知识库分块）。这个代价是可控的，因为只有一处代码需要处理。

### 4. 引用来源为什么用 JSON 而不是独立表

F14 的问答引用溯源要展示"这个回答依据了哪几篇文章"。理论上该建一张 `chat_citation` 表做规范化，但这里选了 JSON 存在消息行上，理由：

- 引用数据**永远是和消息一起读出来的**，不存在单独查询引用的场景
- SQLite 有 JSON1 支持，真要按引用查也能查（`json_each`）
- 少一张表、少一次 join

而且把文章标题也冗余存进 JSON 里，还有个额外好处：**文章被删了以后，历史回答的引用来源仍然显示得出来**。

```json
[{"article_id": 3, "title": "租房合同要注意什么", "score": 0.87}]
```

### 5. 为什么所有业务表都不加 user_id

功能清单第四节把用户标为「全局」，实现时我更进一步：**连 user_id 外键都不加**。

因为功能清单 2.4 的 N1 已经明确"多用户注册与多租户"是不做的。只有一个人的系统里，`user_id` 恒等于 1，加了它意味着每一次查询都要多带一个恒真的 WHERE 条件、每个索引都要多一列，纯属噪音。

这是一个明确的取舍：**放弃了"以后加多用户时不用改表"的便利，换取了现在所有查询都干净**。如果哪天真的要加，就是一次迁移加字段加回填，SQLAlchemy 和 Alembic 都支持，不是重写。

### 6. 搜索为什么先不用 FTS5

技术栈文档选 SQLite 的一个理由是它支持 FTS5 全文检索。**这个能力在，但这一版不启用**，F8 的关键词搜索先用 `LIKE '%关键词%'`。

原因是 FTS5 的中文分词有实实在在的坑：

- 默认的 `unicode61` 分词器按空格和标点切词，中文整段会被当成一个巨大的词，**搜什么都搜不到**
- 换 `trigram` 分词器（按三字切片）能搜中文，但**两字词搜不了**——而"租房""省钱"这种两字词恰恰是最常用的
- 要做对，得引入 jieba 之类的分词库，在写入时就把正文切好词存进一个额外字段

而这些复杂度换来的收益，在当前数据量下是零：

- F8 明确要求搜索结果是**按时间倒序**，不是按相关度——FTS5 最大的价值 BM25 排序用不上
- 个人知识库撑死几千篇文章、约十几 MB 文本，`LIKE` 全表扫描几十毫秒，你感觉不到

**什么时候该启用**：当文章超过大约一万篇、搜索明显卡顿，或者你想做"按相关度排序"和"关键词 + 向量混合检索"时。到那时是一次独立的迁移，不影响现有数据。

## 七、数据完整性：哪些靠数据库，哪些靠代码

### 7.1 外键：声明但不校验

SQLite 的 `PRAGMA foreign_keys` 默认是 **OFF**，外键声明存在但不生效。本项目**保持这个默认，不开启校验**。

但外键仍然在模型里声明、在表结构里存在，这是有意的：

- **SQLAlchemy 靠 ForeignKey 自动推导表之间的关系。** 不声明的话，每个 `relationship()` 都要手写 join 条件，代码量翻倍，出错概率也高得多
- **哪天想启用校验，改一行 PRAGMA 即可。** 约束本来就在表结构里，不需要重建表、不需要迁移
- 声明本身也是文档：读模型代码时能一眼看出表之间怎么关联

**代价必须清楚——下面这些保护你现在是没有的：**

| 你可能会做的事 | 开启校验的话 | 当前（不校验） |
|----------------|--------------|----------------|
| 插入 `category_id` 指向不存在分类的文章 | 数据库直接拒绝 | **静默写入**，读的时候分类显示为空，不报错 |
| 删除还有文章在用的分类 | 数据库直接拒绝 | 分类没了，那些文章变成分类显示不出来的孤儿 |
| 删除文章 | 数据库自动清掉它的标签关联 | 需要靠 ORM 关系清理，见 7.3 |
| 删除会话 | 数据库自动清掉它的消息 | 同上 |

### 7.2 靠数据库保证的

| 约束 | 说明 |
|------|------|
| 非空 | 所有标了「非空」的字段，写入空值直接被拒 |
| 唯一 | `user.username`、`category.name`、`tag.name`、`(article_id, chunk_index)` |
| 主键唯一 | 所有表 |

**注意：外键和级联删除不在这张表里** —— 它们声明了但不生效。

### 7.3 靠代码保证的

| 约束 | 怎么做 |
|------|--------|
| **引用完整性** | 删分类前先查有没有文章在用；写入文章前确认分类存在。这类检查集中在各模块的 `service.py`，不要散落到 router 里 |
| **级联清理** | 用 SQLAlchemy 的 ORM 关系：多对多中间表用 `secondary`（SQLAlchemy 会在删除任一端时自动清理关联行）；一对多用 `cascade="all, delete-orphan"`。ORM 级联在 Python 层执行，不受 PRAGMA 影响 |
| 枚举值合法性 | SQLite 改 CHECK 约束要整表重建，而这些值将来可能增加。用 Python 枚举 + Pydantic 校验 |
| `article.content_text` 由 `content_html` 正确抽取 | 是业务逻辑，不是数据约束。两个字段必须在同一个 service 函数里一起写，见第八章风险表 |
| `knowledge_chunk.article_id` 指向的文章存在 | 软引用，本来就不建外键，见第六章第 3 条 |
| 软删除的一致性（`status='deleted'` 时 `deleted_at` 必须有值） | 属业务规则 |
| 密码强度、标题长度上限 | 在接口层拦截并给出友好提示，而不是让用户撞数据库报错 |

### 7.4 这条取舍什么时候该重新考虑

如果出现下面任一情况，就该把 `PRAGMA foreign_keys = ON` 打开：

- 你发现过一次「明明写错了但没报错，等读的时候才发现」的坏数据
- 项目从单人自用变成有别人一起维护，代码里的检查不再可靠
- 你开始写批量导入 / 数据迁移脚本，绕过了 service 层

打开的方式是在 `core/database.py` 里加一个连接事件监听器统一设置——因为约束本来就在表结构里，这一步不需要任何迁移。

## 八、风险与注意事项

| 类型 | 内容 | 应对建议 |
|------|------|----------|
| 风险 | **外键不校验，引用完整性全靠代码**（这是本项目的主动取舍） | 所有涉及删除 / 引用写入的操作集中在 `service.py`，不要在 router 里直接操作数据库。判断标准很简单：**任何删除操作，都要先问一句「有没有别的表在引用它」** |
| 风险 | 时间字段混入本地时间，导致排序错乱 | 所有 `DATETIME` 一律用 `datetime.now(timezone.utc)` 生成；代码审查时看到 `datetime.now()` 不带参数就是 bug |
| 风险 | `planned_date` 被当成时间戳处理 | 它是日历日期。存 `date` 对象不是 `datetime`，任何时区转换都会让它偏移一天 |
| 风险 | 忘记把 `content_text` 和 `content_html` 一起更新 | 放在同一个 service 函数里写，不要给调用方留"只更新一个"的可能 |
| 风险 | 换 embedding 模型后新旧向量混用 | `vector_dim` 和 `embedding_model` 两个字段就是为此准备；重建时只处理不匹配的块 |
| 风险 | SQLite 单文件损坏或无备份 | 每周复制 `backend/data/` 到网盘。**这是唯一一条出事完全无法挽回的风险** |
| 风险 | 文章量增长后 `LIKE` 搜索变慢 | 按第六章第 6 条的触发条件启用 FTS5，是一次独立迁移 |

## 九、下一步

本文档只定义了表结构，还没有生成任何数据库对象。接下来要做的是：

1. **写 SQLAlchemy 模型**：按模块归属分别写进 `app/core/models.py`（user）和三个模块各自的 `models.py`
2. **配置 Alembic**：初始化迁移环境，并在 `alembic/env.py` 里遍历模块注册表导入所有模型——**不写这一步，自动生成的迁移脚本会是空的**（架构设计第九章风险表第一条）
3. **生成并执行初始迁移**：产出建表脚本，检查无误后执行
4. **创建初始账号**：写一条命令行脚本，交互式输入账号密码，用 core 的 `security.hash_password` 生成哈希
5. **验证**：用一个临时脚本插入分类、标签和文章，确认多对多关联能正常写入，删除文章时标签关联行被正确清理

第 5 步不能省，而且要验的正是 7.1 那张表里的第三行——**删文章时标签关联有没有被清掉，是唯一必须实际跑一遍才知道的事**。因为外键不校验，数据库不会帮你兜底，清不掉就是清不掉，只会攒下一堆垃圾行。
