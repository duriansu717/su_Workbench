## 三、选型理由与备选对比

### 3.1 前端框架

- **选中方案**：Vue 3.5.43
- **选型理由**：这是你指定的技术偏好。Vue 3 的 Composition API 很适合按模块组织代码，每个模块可以把自己的组件、状态、路由放在一起，正好匹配功能清单第六节要求的"模块化竖切"。中文文档和社区在国内是最厚的，遇到问题最好搜。
- **备选方案**：React 19.x
- **放弃原因**：你已明确选 Vue；且 React 生态更分散（路由、状态管理都要自己挑一套），对单人项目反而多出选择成本。

### 3.2 后端框架

- **选中方案**：FastAPI 0.141.1
- **选型理由**：三个理由恰好命中你的三个需求。一是 `APIRouter` 可以一个模块一个路由文件，再由模块注册表统一挂载，这正是功能清单第六节要的"模块清单驱动"；二是自动生成 Swagger 接口文档，前端联调时不用手写文档；三是 Pydantic 自动做请求校验，少写大量验证代码。
- **备选方案**：Flask 3.x、Django 5.x
- **放弃原因**：Flask 太裸，校验、文档、异步都要自己拼，反而多装插件；Django 自带 ORM、后台、认证全套，但它的"大而全"和你要的"轻量、按模块自由生长"方向相反，学它的那套约定比写代码还费时间。

### 3.3 数据库

- **选中方案**：SQLite 3.51.1（Python 内置）
- **选型理由**：这是本次选型里最关键的一条，因为它直接回应你"不想到处下载环境、要省内存"的要求。SQLite **不需要安装、不需要常驻后台进程、不占额外内存**，整个数据库就是项目里的一个文件。功能上它一点不缺：FTS5 支持文章全文检索（F8），JSON1 支持各模块的灵活配置字段，向量以 BLOB 存进表里配 numpy 做余弦相似度（F11）。单人使用没有并发压力，SQLite 完全够。
- **备选方案**：PostgreSQL 17 + pgvector
- **放弃原因**：PostgreSQL 能装，但要在 Windows 上装服务、常驻后台吃内存、还要单独配置 pgvector 扩展。它换来的是高并发和更强的向量索引——而这两样你一个人用不上。**注意**：SQLAlchemy 已经把数据库差异挡在代码之外，如果未来真的需要换，改连接串加少量适配即可，不是重写。

### 3.4 前端语言

- **选中方案**：TypeScript 5.9.3
- **选型理由**：你的第一需求是"随时能加功能、模块之间尽量分离"。TypeScript 就是用来把"模块之间的接口"写死的——以后新增一个模块时，接错字段会在编辑器里直接标红，而不是等到运行时才发现。VSCode 的自动补全也能大幅降低写代码的负担。
- **备选方案**：JavaScript
- **放弃原因**：JS 上手确实更快，但模块一多，改一处不知道哪里会崩，重构成本反而更高。考虑到你的项目定位就是"长期持续加模块"，这一步值得提前付出。
- **版本说明**：本文档 v1.0 定的是 TypeScript 7.0.2（当时 npm 上的 latest）。实际搭建骨架时，vue-tsc 3.3.11 引用 TypeScript 7 已不再暴露的内部路径 `typescript/lib/tsc`，类型检查直接崩溃（`ERR_PACKAGE_PATH_NOT_EXPORTED`）。按第七章预判的应对方案降到 5.9.3 后恢复正常。**这不影响任何架构决策**，只是工具链版本的选择。

### 3.5 富文本编辑器

- **选中方案**：wangEditor `@wangeditor/editor` 5.1.23 + `@wangeditor/editor-for-vue` **5.1.12**
- **版本坑（务必记住）**：`@wangeditor/editor-for-vue` 有**两条平行的版本线**，而 npm 的 `latest` 标签指向的是 **Vue 2** 那条：

  | 版本 | vue peer | 对应 |
  |------|----------|------|
  | `0.x` / `1.x`（`latest` 指向 1.0.2） | `^2.6.14` | Vue 2 |
  | `5.1.x`（`next` 标签指向 5.1.12） | `^3.0.5` | **Vue 3** |

  文档 v1.0/v1.1 里写的 `1.0.2` 是照着 `latest` 标签抄的，实际装的时候直接报 peer 冲突。**装这个包必须显式指定 5.1.x，不能用默认的 latest。**
- **选型理由**：开箱即用——自带完整工具栏，装完就能写，不需要自己搭 UI。中文文档、中文社区，出问题好搜。对"生活小问题记录"这种场景，功能刚好够用。
- **备选方案**：TipTap 3.31.3、Quill 2.0.3
- **放弃原因**：TipTap 能力更强、社区更活跃，但它是 headless 的，工具栏和按钮要自己从头搭，对第一阶段是明显负担；Quill 2 的 Vue 3 集成需要自己包一层。**提醒**：编辑器存的 HTML 是可移植的，以后想换编辑器，已有文章的正文不用重新处理，所以这个选择不是不可逆的。

### 3.6 认证方案

- **选中方案**：PyJWT 2.15.1 + bcrypt 5.0.0，token 放 httpOnly Cookie
- **选型理由**：单账号登录不需要完整的用户体系，JWT 签发一个长期 token 就够。放 httpOnly Cookie 而不是 localStorage，是因为你的应用要渲染富文本 HTML——万一有 XSS，localStorage 里的 token 会被脚本直接读走，httpOnly Cookie 读不到。
- **备选方案**：服务端 Session
- **放弃原因**：Session 需要额外的存储和管理逻辑，对单账号场景是多余的一层。bcrypt 直接用，不用 passlib——passlib 已长期不维护。

### 3.7 向量检索

- **选中方案**：向量存 SQLite 的 BLOB 字段，检索时读进内存用 numpy 2.5.3 算余弦相似度
- **选型理由**：你的知识库规模是"自己写的文章"，量级大概在几百到几千个分块。这个规模下暴力算相似度只要几十毫秒，完全不需要专门的向量数据库。**少一个依赖，少一个要理解和维护的东西**。
- **备选方案**：sqlite-vec 0.1.9
- **放弃原因**：它能让向量检索留在数据库里，但它目前还是 0.x 版本，API 未稳定。你的数据量根本用不到它的性能优势，等以后分块数上万、暴力算确实变慢了，再引入它——因为向量本来就存在 SQLite 里，升级不需要迁移数据库。
- **实测数据**（2026-09-29 在本机 Python 3.13.12 + numpy 2.5.3 实测，1024 维 float32 向量）：

  | 向量数量 | 占内存 | 单次暴力检索耗时 |
  |----------|--------|------------------|
  | 2,000 | 7.8 MB | 0.31 ms |
  | 16,000 | 62.5 MB | 3.68 ms |
  | 50,000 | 195.3 MB | 13.42 ms |

  向量以 BLOB 存入 SQLite 再取回，与内存中原始数据逐字节一致（`np.array_equal` 为 True，无损）；16000 个向量的数据库文件约 70 MB。
- **为什么这个数字够用**：一次 embedding API 调用（把问题转向量）通常耗时 100-500ms，向量检索在这个量级下只占整个问答流程耗时的 1% 以内，**根本不是瓶颈**。
- **实现注意**：从磁盘读回 16000 个向量约需 192ms，比检索本身还慢。因此服务启动时应把向量一次性读入内存缓存，之后每次问答只需上表中的耗时。代价为约 62.5 MB 常驻内存，仍远低于单独运行一个数据库服务的开销。

### 3.8 部署方式

- **选中方案**：不用容器。开发时前后端两个进程，日常使用时前端构建成静态文件由 FastAPI 一起托管
- **选型理由**：这是"轻量化"要求的直接落点。Docker Desktop 在 Windows 上要靠 WSL2 跑一个虚拟机，开机常驻吃几个 G 内存——正好是你想避免的东西。而 FastAPI 本身就能托管静态文件，构建完的前端和接口跑在同一个进程、同一个端口，不需要额外装 Nginx。
- **备选方案**：Docker + Nginx；FlyEnv 这类本地环境管理器
- **放弃原因**：Docker Desktop 在 Windows 上要靠 WSL2 跑虚拟机，开机常驻 2-4GB 内存，正是要躲开的东西；Nginx 对单人项目是多余一层。FlyEnv 是优秀的原生替代方案（开源免费，官方称约 200-400MB 内存），但它擅长管理 PHP / MySQL / Nginx / Redis 这类需要常驻服务的栈，而本项目全部技术栈是 Python + Node + SQLite，**没有任何一项需要被它管理**；装了反而多出一层「环境归属」的困惑。评估结论：本项目不装，等以后需要多版本运行时切换时再考虑。

## 五、版本控制规范

### 5.1 分支模型

| 分支名 | 用途 | 生命周期 |
|--------|------|----------|
| main | 始终可运行的版本。只接受来自 dev 的合并，每次合并打一个 tag | 长期 |
| dev | 集成分支。功能做完先合到这里，自己点一遍确认没问题 | 长期 |
| feature/* | 单个功能开发，如 `feature/module-shell`、`feature/article-editor` | 功能完成后删除 |
| fix/* | 修 bug，如 `fix/login-token-expire` | 修复完成后删除 |

### 5.2 提交信息规范

采用 Conventional Commits，格式：`<type>(<scope>): <描述>`

| type | 含义 | 示例 |
|------|------|------|
| feat | 新功能 | feat(article): 增加富文本编辑器 |
| fix | 修 bug | fix(auth): 修复 token 过期后没跳登录页 |
| docs | 文档 | docs: 更新功能清单到 v1.1 |
| style | 格式调整，不影响逻辑 | style: 统一缩进 |
| refactor | 重构 | refactor(core): 抽出模块注册表 |
| test | 测试 | test(article): 补充分类筛选用例 |
| chore | 构建 / 依赖 / 配置 | chore: 升级 vite 到 8.3.1 |

type 和描述用中文，scope 用英文。**scope 统一用模块名**：`core`（骨架）、`auth`（登录）、`article`（文章）、`plan`（计划）、`ai`（问答）。这样以后 `git log --oneline --grep="feat(plan)"` 就能直接拉出某个模块的全部历史，和模块化架构是配套的。

### 5.3 合并与评审流程

单人项目没有别人帮你 review，所以第 3 步必须自己认真做——它是你唯一的防线。

1. 从 dev 切出功能分支：`git switch -c feature/article-editor`
2. 写完自测通过后提交：`git commit -m "feat(article): 增加富文本编辑器"`
3. **合并前自查 diff**：`git diff dev`。重点看三件事——有没有误提交的密钥（`.env`）、有没有忘记删的调试代码（`print` / `console.log`）、有没有把 `data/` 里的数据库文件加进来
4. 切回 dev 合并，用 `--no-ff` 保留功能分支的完整记录：`git switch dev && git merge --no-ff feature/article-editor`
5. 功能稳定后合并回 main 并打 tag：`git switch main && git merge --no-ff dev && git tag -a v0.1.0 -m "文章模块完成"`，然后删掉已合并的 feature 分支

## 六、环境与依赖管理

### 6.1 环境划分

| 环境 | 用途 | 运行方式 | 数据 |
|------|------|----------|------|
| 本地开发 | 日常写代码、调试 | 两个进程：后端 `uvicorn --reload`（8000 端口）+ 前端 `npm run dev`（5173 端口，配置代理转发到 8000） | 本地 SQLite 文件 |
| 日常使用 | 自己平时真正在用 | 一个进程：`npm run build` 生成静态文件，FastAPI 直接托管，只跑后端 | 同一个本地 SQLite 文件 |

> 单人项目只保留这两个环境，不引入预发、灰度、测试环境——那些是团队协作才需要的。日常使用时前端不走开发服务器，因为静态文件已经构建好了，少一个进程就少占一份内存。

### 6.2 依赖与配置文件清单

| 文件 | 作用 | 是否提交到 Git |
|------|------|----------------|
| requirements.txt | 后端依赖清单，写死版本号 | 是 |
| package.json | 前端依赖清单 | 是 |
| package-lock.json | 前端依赖锁文件 | 是，不要删 |
| .gitignore | 忽略规则 | 是 |
| .gitattributes | 声明行尾统一为 LF，避免 Windows 下每次提交刷一屏警告，也避免以后上 Linux 时因行尾产生整文件的假改动 | 是 |
| .env.example | 环境变量模板，只写字段名不写真实值 | 是 |
| .env | 真实密钥（JWT SECRET_KEY、以后的 AI API Key） | 否，必须写进 .gitignore |
| README.md | 启动与使用说明 | 是 |
| data/*.db | SQLite 数据库文件（你的全部文章和待办都在里面） | **否，必须忽略** |
| .venv/ | Python 虚拟环境 | 否 |
| node_modules/ | 前端依赖 | 否 |
| dist/ | 前端构建产物 | 否 |
| uploads/ | 文章插图上传目录 | 否 |

### 6.3 依赖版本锁定

- **后端**：requirements.txt 里写死版本号，用 `fastapi==0.141.1` 而不是 `fastapi>=0.141`。理由：单人项目最怕"昨天还好好的，今天装完依赖就跑不起来了"
- **前端**：package-lock.json 提交到 git，绝对不要删。它保证你换电脑、重装时能装到一模一样的版本
- **更新频率**：每 2-3 个月，挑一个功能刚做完、系统稳定的时候统一更新一次。**不要边写功能边升级依赖**——出了问题你分不清是新功能写错了还是依赖变了
- **更新前的安全动作**：先 `git add . && git commit` 把当前状态存下来，再执行更新。升完跑一遍主要功能，出问题直接 `git reset --hard` 回到刚才的提交

## 七、风险与注意事项

| 类型 | 内容 | 应对建议 |
|------|------|----------|
| 版本风险 | ~~TypeScript 7.0.2 与 vue-tsc 3.3.11 不兼容~~ **已发生，已解决** | 搭建骨架时 `npm run type-check` 报 `ERR_PACKAGE_PATH_NOT_EXPORTED: typescript/lib/tsc`。已降到 TypeScript 5.9.3 并实测通过。`vite build` 不受影响（Vite 用 esbuild，不走 tsc），所以构建一直是好的，只有类型检查会崩 |
| 依赖风险 | pip 直接连 PyPI 在国内网络下极慢，实测卡了十几分钟一个包都没下下来 | 加 `-i https://pypi.tuna.tsinghua.edu.cn/simple` 后几秒装完。建议一次性配好镜像源，见第八章第 2 步 |
| 依赖风险 | vite.config.ts 用到 `node:url`，缺少 Node 类型声明时类型检查报 TS2307 | 安装 @types/node 26.6.3，并在 tsconfig 的 `types` 数组里加上 `"node"`（只装包不够——`types` 字段会限制自动加载范围） |
| 版本风险 | FastAPI 仍是 0.x 版本号，小版本之间偶有破坏性变更 | requirements.txt 写死版本号；升级前先看官方 release note |
| 版本风险 | 各版本号是 2026-09-29 查询的，过一段时间就会过时 | 安装前到官方 release 页核对一次；本文档更新时版本号递增到 v1.1 |
| 依赖风险 | 你机器上全局已装 pydantic 2.12.4、PyJWT 2.10.1，与本项目要用的版本不一致 | 项目一律使用 `.venv` 虚拟环境，**不要往全局 Python 里装任何东西**，否则以后别的项目会互相打架 |
| 依赖风险 | 国内网络环境下 pip / npm 装包可能慢或失败 | 一次性配置国内镜像源（pip 用清华 TUNA，npm 用阿里云），配完就不用再管 |
| **依赖风险** | **npm 的 `latest` 标签不一定是你要的版本**。本项目的 `@wangeditor/editor-for-vue` 就踩了：latest 指向 Vue 2 版本 | 装包前用 `npm view <包名> peerDependencies` 核对它要求的运行时版本；纯前端库还要看它 peer 的是 Vue 2 还是 Vue 3 |
| 流程风险 | `npm install ... \| tail -8` 这类管道会让**退出码变成 tail 的**，安装失败也显示成功 | 检查安装结果要么看日志内容（有没有 `added N packages`），要么用 `${PIPESTATUS[0]}` 取真实退出码。本项目踩过一次，白排查了几分钟 |
| **样式风险** | **显式 `import { ElMessage } from 'element-plus'` 会让它的样式丢失**。Element Plus 的样式是 unplugin 的解析器**按需注入**的，显式导入绕过了这一步 —— 结果是弹窗能弹出来，但完全没有样式，**而且构建不报任何错** | 组件函数（`ElMessage` / `ElMessageBox` / `ElLoading` 等）**不要自己写 import**，交给 `unplugin-auto-import` 注入。验收方法：构建后 `grep -l "el-message" dist/assets/*.css`，能搜到才算真的进来了。本项目踩过一次 |
| 流程风险 | 改完代码**先跑类型检查再跑构建**，会报 `Cannot find name 'ElMessage'` 之类的错 | `auto-imports.d.ts` 是 `vite dev` / `vite build` 时生成的，类型检查依赖它。**先跑一次 dev 或 build，再跑 type-check** |
| 学习成本 | TypeScript 对只学过一点编程的人有门槛 | 先用 Vue 官方脚手架默认配置，把 tsconfig 的 `strict` 关掉降低门槛，等写顺了再逐步打开 |
| 学习成本 | FastAPI 的 async / await 需要理解异步概念 | 本项目几乎全是简单增删改查，第一阶段用同步写法（`def` 而不是 `async def`）完全能跑，不必一上来就啃异步 |
| 学习成本 | Alembic 的迁移概念对新手不直观 | 第一阶段只用两条命令：`alembic revision --autogenerate -m "说明"` 和 `alembic upgrade head`，不深究原理 |
| 部署风险 | **SQLite 是单个文件，删除或磁盘故障就等于全部丢失** | 每周把 `data/` 目录复制一份到网盘或其他盘符。这是你唯一的备份手段，比任何技术选型都重要 |
| 部署风险 | 想让手机访问时，后端跑在电脑上，手机必须和电脑连同一个 WiFi | 第一阶段先在局域网内用；以后想随时随地访问，再考虑上云或内网穿透，那是独立的一次决策 |
| 部署风险 | 未来若上云，SQLite 文件路径和上传目录需要调整 | 数据库路径、上传目录、密钥一律走 `.env` 配置，不写死在代码里；这样换环境只改配置 |
| 部署风险 | 内网访问时若图省事把接口暴露到公网，单账号登录会成为唯一防线 | 先不要开放公网。真要开放，先做 HTTPS 和登录失败次数限制 |

## 八、下一步行动

1. **初始化 Git 仓库**：在项目根目录执行 `git init`，新建 `dev` 分支，并先写好 `.gitignore`（必须包含 `.venv/`、`node_modules/`、`.env`、`data/`、`dist/`、`uploads/`）——先建忽略规则再提交第一次，避免把密钥和数据库误传上去
2. **建后端虚拟环境**：`python -m venv .venv`，激活后依次安装 fastapi==0.141.1、uvicorn==0.54.0、sqlalchemy==2.1.1、pydantic==2.13.5、alembic==1.20.0、pyjwt==2.15.1、bcrypt==5.0.0、python-multipart==0.0.32，装完记进 requirements.txt
3. **建前端工程**：推荐手写工程文件而不是 `npm create vue@latest`（脚手架会生成一堆待删的示例文件）。依赖按第二章的清单锁定版本安装，包括 typescript@5.9.3 和 @types/node
4. **核对安装结果**：`pip list` 和 `npm ls --depth=0` 各跑一遍，确认版本号与本方案一致；若有偏差，先解决偏差再往下走，不要在依赖不确定的状态下开始写业务代码
5. **搭模块化骨架**：按功能清单第六节的模块化约束建立目录结构（后端一个模块注册表 + 模块目录，前端同理），具体结构在下一步的架构设计中给出
6. **首次提交**：`git add . && git commit -m "chore: 初始化项目骨架"`，然后合入 main 并打上 v0.0.1 标签
