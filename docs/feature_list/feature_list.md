## 一、项目概述

| 项目 | 内容 |
|------|------|
| 一句话定位 | 可扩展的个人工作台：用一个统一入口承载我自己不断长出来的各种小工具。首批上线文章、计划清单、AI 问答三个模块，之后随时可以按同一套规范接入新模块 |
| 目标用户 | 我自己（单人使用，单账号） |
| 核心价值 | 一是把零散的生活经验结构化存下来，能检索、能提问；二是它是个能持续长大的容器——想到新功能就直接加进来，不用为每个新想法另起一个项目 |
| 平台形态 | 响应式 Web，一套代码同时覆盖桌面浏览器和手机浏览器 |
| 技术栈建议 | 后端 Python（建议 FastAPI）；前端 Vue 3；AI 问答独立成模块，方便以后换模型。**技术栈必须支撑第六节的模块化扩展约束**，具体框架与版本号在下一步《技术栈选型》中确定 |

## 二、功能分层清单

### 2.1 核心功能（MVP）

> 对应开发第一期：工作台骨架 + 文章模块。**模块化扩展机制必须在这一期落地**——它是后面所有新功能的底座，一期没搭对，后面每加一个功能都要回头改老代码。

| 编号 | 功能名称 | 功能说明 | 用户操作路径 | 输入 | 输出 | 依赖 | 复杂度 |
|------|----------|----------|--------------|------|------|------|--------|
| F1 | 单账号登录 | 用唯一的账号密码进入工作台，未登录时只能看到登录页 | 打开网址 → 输入账号密码 → 提交 → 进入首页 | 账号、密码 | 登录状态凭证 | 无 | 低 |
| F2 | 工作台首页与模块导航 | 登录后的落地页，列出当前已启用的全部模块入口；导航由模块清单生成，不是写死的链接 | 登录 → 首页 → 看到各模块卡片 / 侧边栏 → 点击进入某个模块 | 当前已启用的模块清单 | 模块入口列表 | F1 | 低 |
| F3 | 文章创建与编辑 | 用富文本编辑器写文章，支持标题、加粗、列表、引用、代码块等常见格式，编辑时可选择分类与标签 | 文章模块 → 点「新建文章」→ 填写标题 → 编辑正文 → 选分类、打标签 → 保存 | 标题、正文 HTML、分类、标签 | 一篇已保存的文章 | F2 | 中 |
| F4 | 文章图片上传 | 在富文本编辑器里粘贴或上传图片，插入到正文中 | 编辑正文 → 点插入图片 → 选择本地图片 → 图片出现在正文里 | 图片文件 | 图片访问地址 | F3 | 中 |
| F5 | 文章列表与详情 | 按更新时间倒序浏览所有文章，点进去看完整内容 | 文章模块 → 文章列表 → 点某一篇 → 查看详情 | 页码、每页条数 | 文章摘要列表 / 文章完整内容 | F3 | 低 |

| F8 | 文章搜索与筛选 | 按关键词搜标题和正文，按分类、标签筛选，结果按时间排序 | 文章列表页 → 输入关键词 / 选择分类或标签 → 查看筛选结果 | 关键词、分类 ID、标签 ID | 符合条件的文章列表 | F5、F7 | 中 |

### 2.2 重要功能（增强体验）

> 对应开发第二期和第三期：先做计划清单（F9-F10），再做 AI 问答（F11-F13）。它们都是往一期搭好的模块骨架里**新增**，不应该改动文章模块的代码——这也是检验一期骨架搭得对不对的第一道考题。

| 编号 | 功能名称 | 功能说明 | 用户操作路径 | 输入 | 输出 | 依赖 | 复杂度 |
|------|----------|----------|--------------|------|------|------|--------|
| F9 | 待办事项管理 | 记录待办事项，支持设置计划日期、优先级、勾选完成 | 计划模块 → 点「新增待办」→ 填写标题、日期、优先级 → 保存 → 完成后勾选 | 待办标题、计划日期、优先级 | 待办事项记录 | F2 | 低 |
| F10 | 计划表视图 | 在同一份待办数据上，按日、周、月三种粒度切换查看和排布 | 计划模块 → 切换「日 / 周 / 月」标签 → 查看对应时间段内的待办 | 视图粒度、时间段 | 按时间排布的计划表 | F9 | 中 |
| F11 | 知识库构建 | 把文章正文切块、转向量、存进知识库，文章改动后同步更新 | AI 模块 → 知识库管理 → 点「重建索引」→ 等待完成 → 查看已入库文章数与分块数 | 文章正文纯文本 | 知识库分块与向量 | F3 | 高 |
| F12 | 知识库智能问答 | 用自然语言提问，系统在我的文章里检索相关内容，交给模型生成回答 | AI 模块 → 输入问题 → 发送 → 查看回答 | 问题文本 | 基于自己文章生成的回答 | F11 | 高 |
| F13 | 知识库外开放提问 | 知识库里没有相关内容的提问，转由通用模型回答，并明确标注这不是来自我的文章 | AI 模块 → 输入问题 → 系统判断知识库无匹配 → 返回通用模型回答，页面标注「未引用你的文章」 | 问题文本 | 通用模型生成的回答 + 未引用提示 | F2 | 中 |

### 2.4 明确不做（Out of Scope）

| 编号 | 不做的内容 | 原因 |
|------|------------|------|
| N1 | 多用户注册与多租户 | 单人自用，加多用户要做数据隔离和权限校验，工作量翻倍而收益为零 |
| N2 | 原生 App 与微信小程序 | 本期用响应式 Web 覆盖手机端，原生方案要额外维护一套代码 |
| N3 | 文章分享链接与协作编辑 | 没有协作场景；公开分享还牵扯到权限和隐私，先不碰 |
| N4 | 独立全文检索引擎（如 Elasticsearch） | 个人数据量级用数据库自带的全文索引完全够用，引入独立引擎是过度设计 |
| N5 | 第三方登录（微信 / GitHub） | 单账号自用，邮箱密码足够；接入第三方要走应用审核，不值得 |
| N6 | 计划的甘特图、日历拖拽排期 | 日 / 周 / 月三种列表视图已经够用，拖拽排期交互复杂度高、收益低 |
| N7 | 后台可视化模块管理（在页面上动态增删模块） | 模块清单用一份配置文件维护就够，做成可视化管理系统属于过度设计。注意与 F18 区分：F18 只控制已存在模块的显示开关，不改代码 |
| N8 | 插件热插拔（不重启服务就加载新模块） | 个人工具没有这个需求，新模块通过正常发版上线即可 |
| N9 | 模块市场 / 第三方插件体系 | 只服务我自己一个人，不存在第三方开发者，做插件协议是纯浪费 |

## 三、用户角色与权限

| 角色 | 说明 | 可操作功能 |
|------|------|------------|
| 我自己（唯一账号） | 系统里只有一个账号，登录后对全部模块的数据有完整读写权限。**以后新增的任何模块都沿用这一套权限模型**，不需要为单个模块单独配权限 | F1 ~ F19 全部功能，以及后续新增模块的全部功能 |
| 未登录访客 | 没有账号的人，包括搜索引擎爬虫和误入的路人 | 仅能访问登录页面，看不到任何模块的内容 |

## 四、数据实体清单

| 实体 | 说明 | 关键字段 | 关联实体 |
|------|------|----------|----------|
| 用户 | 【全局】工作台的唯一使用者，不归属任何模块，所有模块共用 | 用户 ID、账号、密码哈希、创建时间 | 无 |
| 分类 | 【文章模块】文章的一级归属，一篇文章只能属于一个分类 | 分类 ID、名称、排序值、创建时间 | 用户 |
| 标签 | 【文章模块】文章的自由标记，一篇文章可以有多个标签 | 标签 ID、名称、创建时间 | 用户 |
| 文章 | 【文章模块】工作台的核心内容 | 文章 ID、标题、正文 HTML、正文纯文本、分类 ID、状态（草稿 / 已发布 / 已删除）、创建时间、更新时间 | 分类、标签、用户 |
| 文章标签关联 | 【文章模块】文章与标签的多对多关系表 | 文章 ID、标签 ID | 文章、标签 |
| 待办事项 | 【计划模块】一条具体的待办 | 待办 ID、标题、备注、计划日期、优先级、是否完成、完成时间、创建时间 | 用户 |
| 知识库分块 | 【AI 问答模块】文章切块后的文本与向量，供问答检索用 | 分块 ID、文章 ID、分块序号、分块文本、向量值、更新时间 | 文章 |
| 问答会话 | 【AI 问答模块】一次连续的对话 | 会话 ID、标题、创建时间 | 用户 |
| 问答消息 | 【AI 问答模块】会话里的单条消息 | 消息 ID、会话 ID、角色（用户 / 助手）、内容、引用文章 ID、是否引用知识库、创建时间 | 问答会话、文章 |

> 模块边界规则：**每个模块只拥有并读写自己的表**，不直接查别的模块的表。模块清单本身存在配置文件里，不建数据库表（见 N7）。

## 五、关键业务流程

1. **记录一篇生活小问题**：
   我 → 登录 → 进入文章模块 → 点「新建文章」 → 填标题、选分类、打标签 → 在富文本编辑器里写正文（需要时插图片） → 保存 → 文章出现在列表页顶部

2. **找回以前记过的一条经验**：
   我 → 进入文章模块 → 输入关键词搜索，或按分类 / 标签筛选 → 点开目标文章 → 看到完整正文

3. **记录并完成一件待办**：
   我 → 进入计划模块 → 新增待办并设置计划日期 → 切换日 / 周 / 月视图查看排布 → 完成后勾选 → 待办标记为已完成

4. **用知识库提问**：
   我 → 进入 AI 模块 → 输入问题 → 系统把问题转向量 → 在知识库中检索最相关的几个分块 → 把分块和问题一起交给模型 → 返回基于我自己的文章生成的回答

5. **问一个知识库里没有的问题**：
   我 → 输入问题 → 检索结果的相似度全部低于阈值 → 系统改走通用模型回答 → 回答下方标注「本回答未引用你的文章」

6. **文章改了之后保持知识库同步**：
   我 → 编辑并保存某篇文章 → 系统标记该文章的分块需要重建 → 触发重新切块与向量化 → 该文章在知识库中更新为新版本

7. **新增一个模块**（工作台的扩展流程，也是架构必须撑住的场景）：
   我 → 提出新模块需求（如记账、书签、健身记录） → 一起确认模块边界和数据实体 → 后端新增一个模块目录（自带路由、业务逻辑、数据表） → 前端新增一个模块目录（自带页面、路由、API 调用） → 在模块清单里登记一行 → 新模块出现在首页导航里 → **已有模块的代码一行都没改**

## 六、技术约束与风险点

| 类型 | 内容 | 应对建议 |
|------|------|----------|
| 约束 | **模块化竖切**：每个功能模块是一条独立的竖线，自带后端路由、业务逻辑、数据表，以及前端页面、路由、API 调用 | 新增模块只新增文件，不修改已有模块；模块之间禁止跨模块直接读对方的数据库表 |
| 约束 | **模块清单驱动**：后端路由挂载和前端导航菜单都由一份模块清单驱动 | 模块清单集中在一处配置文件里，新增模块时只改这一处；不要做成数据库表或可视化后台（见 N7） |
| 约束 | **导航要能容纳未知数量的模块** | 导航由模块清单生成而非写死链接；模块少时用侧边栏，模块多了要能自动收纳或分组 |
| 约束 | **模块间只通过明确定义的接口通信** | 需要别的模块的数据时，走对方暴露的接口或自己复制一份，不要直接 join 别人的表 |
| 约束 | **数据库选型必须一次选对，支撑以后所有模块** | 选型时同时考虑：向量检索（AI 模块）、全文检索（文章模块）、JSON 字段（各模块的灵活配置）。不要等做到 F11 才发现要换库 |
| 约束 | 前后端分离，后端 Python 提供 REST 接口，前端 Vue 消费接口 | 先定接口契约再并行开发，前端不直接接触数据库 |
| 约束 | 一套前端代码同时适配桌面和手机 | 移动端优先设计，用 CSS 断点做响应式；富文本编辑器优先保证桌面端编辑体验，手机端以阅读和轻量修改为主 |
| 约束 | 富文本正文以 HTML 存储 | 保存时同步抽取一份纯文本存入 `正文纯文本` 字段，供搜索和后续 AI 检索使用 |
| 约束 | 后端与 AI 能力解耦 | 模型调用封装成独立服务层，业务代码只依赖抽象接口，方便以后换模型供应商 |
| 风险 | **模块化骨架必须第一期就搭对**，否则后期加模块会退化成重构 | 一期就把模块清单、目录规范、模块间接口约定定下来并写成文档；宁可一期多花时间搭骨架，也不要先写成一整块 |
| 风险 | **过度追求扩展性反而拖慢开发** | 只做「新增模块成本低」这一件事就够了；热插拔、可视化模块管理、插件市场一律不做（见 N7 / N8 / N9） |
| 风险 | 模块变多后前端首屏变慢 | 路由级懒加载，只有访问到的模块才加载它的代码；模块清单体积保持轻量 |
| 风险 | 富文本 HTML 渲染存在 XSS 风险 | 后端保存前做 HTML 白名单过滤，前端渲染时不要裸用 `v-html`，要走过滤后的渲染 |
| 风险 | 富文本 HTML 直接喂给 AI 检索会严重拉低效果 | 知识库只使用 `正文纯文本` 字段切块，绝不使用 HTML；这一点在保存环节就已经准备好 |
| 风险 | AI 问答依赖模型 API，有调用费用和响应延迟 | 先小批量使用并加缓存；问答做成流式输出，避免干等 |
| 风险 | 三个模块一次做完会拖垮单人开发节奏 | 严格按 2.1 → 2.2 → 2.3 推进，每一期结束时系统都必须是可用的 |
| 风险 | 手机浏览器上富文本编辑体验普遍较差 | 接受这个限制：手机端以浏览、搜索、勾选待办为主，重度编辑留给桌面端 |

## 七、开发优先级建议

先做 2.1，而且**这一期的重点不只是文章功能，更是把模块化的骨架搭对**——模块清单、目录规范、模块间接口约定这三样定下来，以后加计划清单、AI 问答，乃至任何一个你现在还没想到的功能，都是「新增一个目录 + 清单里加一行」的事；一期图快写成一整块，后面每加一个模块都要回头动老代码。骨架稳了之后，二期做计划清单（和文章模块完全独立，正好用来验证骨架是否真的好用），三期做 AI 问答（要等文章攒够才有意义，先建库再提问，顺序反了就是个空转的功能）。
